    Aggregated Event Measurement priority

    You get eight conversion event slots per verified domain, ranked. For a user who has opted out of tracking, only the highest-priority event they trigger is reported — so ranking is not cosmetic, it decides what you can optimise for at all.

      Changing the ranking can pause delivery on ad sets optimising for the events you moved, and value optimisation changes carry a cool-down before they take effect. Set this once, deliberately, before you spend money — not mid-campaign.

      Conversions API

      The browser pixel is the copy that gets blocked — by ad blockers, by tracking prevention, by a checkout that happens on someone else's domain. The server copy is the one that survives. You send both, and deduplicate.

      How deduplication actually works

      Two copies of one event collapse into one when both of these match:

      • event_name — identical string, case-sensitive
      • event_id — identical, and unique per real-world occurrence

      In browser code the field is called eventID (in the fbq options object). On the server it is event_id. Same value, two names — this trips up most first implementations.

      The failure that doubles your numbers: generating the ID separately on each side. Date.now() in the browser and uuid() on the server will never match, so every purchase is counted twice and every reported CPA is half of what you're really paying.
      The fix: generate the ID once, server-side, and use something you already have — an order ID, a lead ID, a submission ID. It's naturally unique, it's identical on both sides by construction, and it's idempotent if the page reloads or the webhook retries.

      Deduplication is evaluated over a rolling window of roughly 48 hours, so a server event that arrives minutes or hours late still merges with its browser twin. Send the server copy anyway even when you're confident the browser fired: a duplicate that deduplicates costs nothing, a missing event costs you a conversion.

      User data — what makes matching work

      hash everything marked SHA-256

      Meta can only credit a conversion to an ad if it can match the event to a person. More matchable fields, sent consistently, is the single biggest lever on Event Match Quality — and on how much of your real performance you ever see.

      KeyFieldNormalise toHashedWeight
      Normalise before hashing, every time, on every platform that sends events. A hash of "Ada@Example.com " and a hash of "ada@example.com" are two unrelated 64-character strings, and the mismatch is invisible — you just quietly match fewer people.

      Before you trust the numbers

      1. Add a test_event_code from Events Manager → Test events to your server payload and confirm the event arrives, with the parameters you expect, in the live view.
      2. Remove that code before going live. Events sent with a test code are for testing and are not what you want flowing through your production traffic.
      3. Trigger one real end-to-end conversion. In Events Manager the event should show both browser and server as connections, and a deduplication figure — not two separate counts.
      4. Check Event Match Quality after 24–48 hours. Below about 5.0 means your matching is leaking; the user-data table above is the fix list.
      5. Compare event counts against your own database for a week. Pixel-only will undercount. Pixel plus a correctly deduplicated server feed should land close.

      The constraint everything else obeys

      learning phase

      An ad set needs roughly 50 optimisation events in a rolling 7 days before Meta's delivery system stops exploring and settles. Under that, it stays in Learning limited: unstable cost, unreliable results, and no read you can act on.

      That converts directly into a budget floor per ad set:

      daily budget per ad set  =  50 × target cost per conversion ÷ 7
