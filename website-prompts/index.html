The fourteen decisions

An AI builder never asks for what it wasn't given. Leave a decision out and it doesn't stop — it picks one, silently, and every prompt after that inherits the pick. This tab is the list of decisions it will make on your behalf. Answer them here once and the other tabs write themselves.

Project

Specificity

—

Weights, not measurements. Each decision carries a weight — how much of the build it steers — and the score is the weighted share you've answered. The weights are this app's judgement, printed next to each decision so you can disagree with them. Nothing here is derived from a benchmark, and no benchmark exists for "how vague was that prompt".

The rules file

The single most useful artefact in this kit, and the one nobody writes. Every builder has a place to put standing instructions — Lovable's Knowledge, a Cursor rules file, an AGENTS.md, v0's project instructions, or just a message you re-paste. Constraints put there apply to every turn; constraints typed into one message decay within three.

Rules for your builder

— 


  


  

    Rules are not magic and they are not enforcement. A model can ignore any of these,
    and long rules files get skimmed like long emails. Short, concrete and testable beats
    thorough: "no gradients" survives; "follow good design principles" does nothing. The
    acceptance checks exist because the rules will occasionally be ignored.

      what it needs answered first, and how much of the build it can damage if it goes wrong.
      Open one, read it, copy it — and change it, because a prompt you haven't read is a decision
      you haven't made.

Build order

    

      Order is not a nicety. Whatever exists when you ask for the next thing is the context for
      it, so the first prompt that touches colour decides colour for the whole site, and a page
      built before the design system gets its own private one. The gates below refuse to open
      until the thing they depend on is accepted.

When it goes wrong

    

      Twenty failure modes, each with what actually caused it and the prompt that repairs it.
      The instinct — "that's broken, fix it" — is the single most expensive message you can send:
      it hands the model an unbounded problem and full permission to rewrite anything.
    

  


  

    

      
      
    

  


  


  

    The rule behind every repair prompt here. Name the file, name the symptom, name the
    boundary. "In Pricing.tsx only, the middle card is 12px taller than the others;
    fix that and change nothing else" beats "the pricing looks off" every single time — not
    because the model is stupid, but because the second version genuinely does not say what
    "right" is.
  







  

    
Acceptance checks

    

      What to look at before sending the next prompt. Accepting a phase you haven't checked is
      how a small fault becomes the foundation for six more prompts — and the fix, by then, is a
      rebuild rather than an edit.

What vagueness costs

    

      Builders charge by the message, the credit or the month, and a redo costs exactly what the
      original did. So the price of an under-specified prompt is not a worse site — it's the
      three further messages spent undoing a default you never chose, plus your own time
      reading each result.

How the arithmetic works

    

  


  

    Prices go stale; the shape doesn't. Every price above is yours to type — this app ships
    no price list, because builder pricing changes every few months and any figure baked in here
    would be wrong by the time you read it. What doesn't change is that a redo costs a full
    message, and that the expected number of attempts at something that fails a fraction
    p of the time is 1/(1−p) — which climbs slowly until p passes about a
    half, and then very fast indeed.

      Nine tools that will all write you a website, differing less in model quality than in what
      they lock you into. The prompts in this kit work in any of them; what changes is what you
      can ask for, and what you own afterwards.

What this kit is not

    
    
      
  • Not a guarantee of a good site. It removes one specific failure — the model
        deciding things you should have decided — and leaves every other one in place.
    • 
      
  • Not a substitute for looking at the result. Every prompt here ends up in an
        acceptance check for exactly that reason.
    • 
      
  • Not a code review. Generated code can be shaped correctly and still be wrong;
        the checks catch what a person can see in a browser, not what a security audit would.
    • 
      
  • Not tied to any one tool. Nine builders are described and none is recommended,
        because the right answer depends on whether you ever want to leave.
